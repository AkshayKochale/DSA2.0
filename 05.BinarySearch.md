# <span style="color:orange">  Binary Search </span>

## 1. Problem Statement
LeetCode 704 / NeetCode "Binary Search". Given an array `nums` of **distinct** integers sorted in ascending order and an integer `target`, return the index of `target` if it exists, otherwise `-1`. Must run in O(log n) time.
Example: `nums = [-1,0,2,4,6,8], target = 4` -> `3`; `target = 3` -> `-1`.
Constraints: `1 <= nums.length <= 10000`, `-10000 < nums[i], target < 10000`, all values unique. Recommended: O(log n) time, O(1) space.

## 2. My Approach
My submitted code (unmodified):

```java
class Solution {
    public int search(int[] nums, int target) {
        
           int s=0,e = nums.length-1;

            while(s<=e){
                int mid =(s+e)/2;
                // int mid = s + (e - s) / 2;
                if(nums[mid]==target)return mid;
                else if(nums[mid]<target)s= mid+1;
                else e = mid-1;
            }

           return -1; 
    }
}
```

Classic binary search on the closed interval `[s, e]`. Compare the middle element with the target: equal returns the index, smaller moves `s` right of `mid`, larger moves `e` left of `mid`. When the interval is empty, return `-1`.

## 3. Complexity
- Time: O(log n)
- Space: O(1)
- Correct. Hand-traced on both examples, a single element, and a target smaller or larger than every element.

## 4. What I Missed
No correctness problems. Remaining points:
- **The active `mid` line is the overflow-prone one**; the safe one is commented out. Use `int mid = s + (e - s) / 2;` as the default habit.
- **Why the two formulas are the same:** `s + (e - s) / 2 = (s + e) / 2` mathematically, and for non-negative `s <= e` integer division gives the same index (with `d = e - s`: `(2s + d) / 2 = s + d / 2`). They differ only in overflow: `s + e` can exceed `Integer.MAX_VALUE` (2,147,483,647) when both indices are above ~1.07 billion and wraps negative, while `e - s <= n - 1` can never overflow. With `n <= 10000` here, both are safe.
- Famous example: the JDK's own `Arrays.binarySearch` and many textbooks had the `(low + high) / 2` bug for years (Joshua Bloch, 2006); the fix was `(low + high) >>> 1`.
- Negative ranges: `(s + e) / 2` truncates toward zero (for `s = -1, e = 0` it gives `0`), while `s + (e - s) / 2` rounds down (gives `-1`). This can cause infinite loops in "binary search on the answer" patterns such as `e = mid` / `s = mid + 1`, so prefer `s + (e - s) / 2`.
- Did not state the **loop invariant**: if `target` exists, its index is inside the closed interval `[s, e]`.
- Did not state why the bounds are `<=` and `mid +/- 1`: with a closed interval, `s == e` still holds one candidate (`<=`), and `mid` has been checked and ruled out, so moving to `mid +/- 1` guarantees the interval shrinks every iteration (no infinite loop).
- Good, keep: the early `return mid`, and the `-1` fallthrough.

## 5. Optimal Approach
Binary search on the closed interval `[s, e]`, maintaining the invariant that `target`, if present, lies inside it. Take `mid = s + (e - s) / 2`. If `nums[mid] == target`, return it. If `nums[mid] < target`, everything at or left of `mid` is too small (sorted), so `s = mid + 1`. Otherwise everything at or right of `mid` is too large, so `e = mid - 1`. Each step halves the interval: O(log n) time, O(1) space.

## 6. Optimal Java Code

```java
class Solution {
    public int search(int[] nums, int target) {
        int s = 0, e = nums.length - 1;
        while (s <= e) {
            int mid = s + (e - s) / 2;          // overflow-safe midpoint
            if (nums[mid] == target) return mid;
            else if (nums[mid] < target) s = mid + 1;
            else e = mid - 1;
        }
        return -1;
    }
}
```

## 7. Quick Revision
Keep the invariant "target, if present, is inside the closed interval `[s, e]`": `mid = s + (e - s) / 2`; equal returns; smaller means `s = mid + 1`; larger means `e = mid - 1`; loop while `s <= e`; else `-1`.
Use `s + (e - s) / 2` because `s + e` can overflow; it is the same value otherwise.

## 8. Pattern
- Primary: Binary Search (closed interval, halve the search space each step)
- Secondary: Loop invariants, Overflow-safe midpoint

# <span style="color:orange">  Koko Eating Bananas </span>

## 1. Problem Statement
LeetCode 875 / NeetCode "Koko Eating Bananas" (`eating-bananas`). Given an array `piles` (bananas in each pile) and `h` hours, Koko picks an eating rate `k` bananas per hour. Each hour she picks one pile and eats up to `k` bananas from it; she cannot move to another pile in the same hour. Return the minimum integer `k` such that she eats all the bananas within `h` hours.
Examples: `piles = [1,4,3,2], h = 9` -> `2`; `piles = [25,10,23,4], h = 4` -> `25`.
Constraints: `1 <= piles.length <= 10,000`, `piles.length <= h <= 1,000,000,000`, `1 <= piles[i] <= 1,000,000,000`. Recommended: O(n log m) time, O(1) space (m = max pile).

## 2. My Approach
My submitted code (unmodified):

```java
class Solution {
    public int minEatingSpeed(int[] arr, int h) {
        
        int n =arr.length;
        Arrays.sort(arr);

        int s=1, e=arr[n-1]; long ans = Long.MAX_VALUE;

        while(s<=e){
            int mid = s+(e-s)/2;

            long tt =calNextPile(arr,mid);

            if(tt<=h){
                 ans = Math.min(ans,mid);
                 e = mid-1;
            }
            else s = mid+1;
                 
        }

        return (int)ans;
    }

    public static long calNextPile(int arr[],int k){
        long tt=0;

           for(int i=0;i<arr.length;i++){
                tt+= arr[i]/k;
                if(arr[i]%k!=0)tt++;
           } 

        return tt;
    }
}
```

Sort the piles only to read the maximum. Binary search the speed `k` in `[1, max]`. For each `mid`, compute the hours needed as the sum of `ceil(pile / mid)` (in a `long`). If the hours are within `h`, record `mid` and search lower; otherwise search higher.

## 3. Complexity
- Time: O(n log n) for the sort + O(n log m) for the search
- Space: O(1) extra, but the sort **mutates the input array**
- Correct. Hand-traced on both examples (answers 2 and 25). Total hours can reach about 10^13, so using `long` was necessary and correct.

## 4. What I Missed
- **The sort is wasted work:** it is used only to read the maximum, costs O(n log n), and reorders the caller's array. One O(n) pass finds the maximum.
- **`ans` bookkeeping is unnecessary:** after every feasible `mid` you shrink `e`, so the last feasible `mid` is already the smallest; `ans = mid` is enough, `int` is enough (the `long` and the `(int)` cast hint at a type mismatch). The lower-bound template (`while (lo < hi)`, `hi = mid` / `lo = mid + 1`, return `lo`) needs no `ans` variable at all.
- **The justification for binary search is unstated:** feasibility is **monotonic**. If speed `k` works, every faster speed also works (hours never increase as `k` grows). That is the whole reason you may discard half of the speeds.
- **Bounds not justified:** lower bound `1` because speeds are positive integers; upper bound `max(piles)` because at that speed every pile takes one hour, giving exactly `n` hours, and `h >= n` is guaranteed, so it is always feasible. Going faster than the largest pile never helps.
- The brute force (`k = 1, 2, 3, ...`) is O(n * m), up to 10^4 * 10^9: far too slow; with `m` as large as 10^9, binary search takes only ~30 iterations.
- Name `calNextPile` is misleading; it computes total hours (`hoursNeeded`).
- Ceil-division alternative without a branch: `(p - 1) / k + 1` for `p >= 1` (avoids the overflow risk of `(p + k - 1) / k`).
- Good, keep: `long` for the hour total, the overflow-safe `s + (e - s) / 2`, and the `/` plus `%` ceil logic.

## 5. Optimal Approach
Binary search on the answer. Define `hours(k) = sum of ceil(pile / k)`. It is non-increasing in `k`, so the set of working speeds is `[k*, max]` and we want the smallest working `k`. Search `k` in `[1, max(piles)]`: if `hours(mid) <= h`, then `mid` works and the answer is `mid` or smaller (`hi = mid`); otherwise it is too slow (`lo = mid + 1`). Stop when `lo == hi`. O(n log m) time, O(1) space.

## 6. Optimal Java Code

```java
class Solution {
    public int minEatingSpeed(int[] piles, int h) {
        int lo = 1, hi = 0;
        for (int p : piles) hi = Math.max(hi, p);         // a speed above the largest pile never helps

        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (hoursNeeded(piles, mid) <= h) hi = mid;    // mid works: try slower
            else lo = mid + 1;                             // too slow: need faster
        }
        return lo;
    }

    private long hoursNeeded(int[] piles, int speed) {
        long hours = 0;
        for (int p : piles) hours += (p - 1) / speed + 1;  // ceil(p / speed) for p >= 1
        return hours;
    }
}
```

## 7. Quick Revision
Binary search on the answer: if speed `k` works then every faster speed works (monotonic), so search `k` in `[1, max(piles)]` (the max always works since `h >= n`). `hours(k) = sum ceil(pile / k)` in a `long`.
`hours <= h` means `hi = mid`, else `lo = mid + 1`; loop `while (lo < hi)`; return `lo`.

## 8. Pattern
- Primary: Binary Search on the Answer (minimum feasible value)
- Secondary: Monotonic feasibility check (greedy O(n)), Ceil division, `long` accumulation to avoid overflow

# <span style="color:orange">  Find Minimum in Rotated Sorted Array </span>

## 1. Problem Statement
LeetCode 153 / NeetCode "Find Minimum in Rotated Sorted Array". An array of unique integers, originally sorted ascending, has been rotated between 1 and `n` times (rotating moves the last elements to the front). Return the minimum element in O(log n) time.
Examples: `[3,4,5,6,1,2]` -> `1`; `[4,5,0,1,2,3]` -> `0`; `[4,5,6,7]` -> `4`.
Constraints: `1 <= nums.length <= 1000`, `-1000 <= nums[i] <= 1000`, all elements unique. Recommended: O(log n) time, O(1) space.

## 2. My Approach
My submitted code (unmodified):

```java
class Solution {
    public int findMin(int[] nums) {
        
        int s =0 ,e =nums.length-1, ans = Integer.MAX_VALUE;

           while(s<=e){

                int mid = s+ (e-s)/2;

                //optimization => when we get range where array is sorted that means we have passes roation point
                if(nums[s]<=nums[e]){
                    ans = Math.min(ans, nums[s]);
                    break;
                }

                // check which part is sorted
                // why equal '='? => possibility that s==mid so '<' will not work
                if(nums[s]<=nums[mid]){
                    ans = Math.min(ans, nums[s]);
                    s = mid+1;
                }
                else {
                    ans = Math.min(ans, nums[mid]);
                    e = mid-1;
                }
           } 


        return ans;
    }
}
```

Binary search that finds which half is sorted. If the whole range is sorted (`nums[s] <= nums[e]`), its first element is the minimum. Otherwise, if the left half is sorted, record its first element and move right; if not, the right half is sorted, so record `nums[mid]` and move left. `ans` keeps the minimum of everything recorded.

## 3. Complexity
- Time: O(log n)
- Space: O(1)
- Correct. Hand-traced on all three examples, plus `[2,1]` and `[1]`. The `<=` in `nums[s] <= nums[mid]` is right: when `s == mid` the left "half" is a single element, which counts as sorted.

## 4. What I Missed
No correctness problems. Remaining points:
- **Simpler template exists:** compare `nums[mid]` with `nums[hi]`. If `nums[mid] > nums[hi]`, the minimum lies strictly right of `mid` (`lo = mid + 1`); otherwise it is at `mid` or to its left (`hi = mid`). Loop `while (lo < hi)` and return `nums[lo]`. No `ans` variable, no early exit, no separate sorted-half case.
- **Predicate view (the real intuition):** define `P(i) = nums[i] <= nums[last]`. For a rotated array of unique values it is `F F F T T T`: the left segment is all larger than the last element, the right segment (which holds the minimum) is all smaller or equal. The minimum is the **first true**; this is binary search on a monotonic predicate, the same idea as Koko Eating Bananas. No rotation means all `T`, so the answer is index 0.
- The invariant behind the code was not stated: the minimum always lies in the remaining interval (or is already recorded in `ans`). Recording the sorted half's first element and discarding that half is safe because the minimum of a sorted half is its first element.
- The "optimization" early exit is valid but not required for correctness (a fully sorted range would be handled by the later branch too). It is also the only thing that stops the loop from re-examining a sorted range.
- Accumulating `ans` across iterations makes the logic harder to reason about than converging `lo` and `hi` onto the answer.
- Follow-up not covered: with **duplicates** (Find Minimum II), `nums[mid] == nums[hi]` is ambiguous, so the comparison logic needs `hi--` and the worst case becomes O(n).
- Good, keep: the comment explaining why `<=` is needed when `s == mid`, and the overflow-safe `s + (e - s) / 2`.

## 5. Optimal Approach
The array is two sorted segments joined at a rotation point; the minimum is the first element of the right (lower) segment. Every element of the left segment is greater than the last element, and every element of the right segment is at most the last element. So comparing `nums[mid]` with `nums[hi]` tells which segment `mid` is in. If `nums[mid] > nums[hi]`, `mid` is in the left segment and the minimum is to its right: `lo = mid + 1`. Otherwise `mid` is in the right segment, so the minimum is at `mid` or before it: `hi = mid`. When `lo == hi`, that index is the minimum. O(log n) time, O(1) space.

## 6. Optimal Java Code

```java
class Solution {
    public int findMin(int[] nums) {
        int lo = 0, hi = nums.length - 1;
        while (lo < hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] > nums[hi]) lo = mid + 1;   // mid is in the left (larger) segment: min is to the right
            else hi = mid;                            // mid is in the right segment: min is at mid or left of it
        }
        return nums[lo];
    }
}
```

## 7. Quick Revision
Compare `nums[mid]` with the last element `nums[hi]`: if `nums[mid] > nums[hi]`, the minimum is strictly right (`lo = mid + 1`); else it is at `mid` or left (`hi = mid`). Loop `while (lo < hi)` and return `nums[lo]`.
Think: the predicate `nums[i] <= last` is `F...F T...T`; the minimum is the first `T`.

## 8. Pattern
- Primary: Binary Search on a monotonic predicate (find the first true) in a rotated sorted array
- Secondary: "Which half is sorted" reasoning (as in Search in Rotated Sorted Array), Converging `lo < hi` template

                    ans = Math.min(ans, nums[s]);

                    continue;

# <span style="color:orange">  Search in Rotated Sorted Array </span>

## 1. Problem Statement
LeetCode 33 / NeetCode "Search in Rotated Sorted Array" (`find-target-in-rotated-sorted-array`). An array of unique integers, originally sorted ascending, has been rotated between 1 and `n` times. Given the rotated array `nums` and an integer `target`, return the index of `target`, or `-1` if it is not present. Must run in O(log n) time.
Examples: `nums = [3,4,5,6,1,2], target = 1` -> `4`; `nums = [3,5,6,0,1,2], target = 4` -> `-1`.
Constraints: `1 <= nums.length <= 1000`, `-1000 <= nums[i], target <= 1000`, all values unique. Recommended: O(log n) time, O(1) space.

## 2. My Approach
My submitted code (unmodified):

```java
class Solution {
    public int search(int[] nums, int t) {

         int s =0, e = nums.length-1;

         while(s<=e){
            int mid =(e+s)/2; 
            if(nums[mid]==t)return mid;

            // check left sorted
            if(nums[s]<=nums[mid]){
                  if(t >= nums[s] && t<nums[mid])
                    e = mid -1;
                else 
                    s = mid+1;   
            }
            // right sorted 
            else{
                  if(t>nums[mid] && t<=nums[e])
                    s = mid+1;
                  else 
                    e =mid-1;    
            }
         }      


    return -1;

    }
}
```

Single-pass binary search. At each step one half of `[s, e]` is guaranteed to be sorted. If the left half is sorted (`nums[s] <= nums[mid]`), check whether the target lies within its range `[nums[s], nums[mid])`: if so go left, otherwise go right. If instead the right half is sorted, check whether the target lies within `(nums[mid], nums[e]]`: if so go right, otherwise go left.

## 3. Complexity
- Time: O(log n)
- Space: O(1)
- Correct. Hand-traced on both examples and on `[3,1]` (targets 1 and 3), `[5,1,3]` target 3, `[1]` target 0, and an absent target above the maximum.

## 4. What I Missed
No correctness problems. This is already the optimal one-pass solution. Remaining points:
- **Active midpoint is `(e + s) / 2`**; the overflow-safe `s + (e - s) / 2` should be the default habit (not a problem at `n <= 1000`).
- **The key invariant was not written down:** a rotated sorted array has a single drop, so any interval `[s, e]` contains at most one drop, and `mid` puts it in at most one half. The other half is plainly sorted, where "is the target in this half?" is just two comparisons against its endpoints. If it is, search that half; if not, it can only be in the other half.
- The `<=` in `nums[s] <= nums[mid]` is needed for the case `s == mid` (a one-element left half is sorted), but unlike the Find Minimum problem there is no comment saying so.
- Boundary correctness worth stating: the sorted-half ranges are `[nums[s], nums[mid])` and `(nums[mid], nums[e]]`: the `mid` side is exclusive because `mid` was already checked for equality.
- Alternative not mentioned: two binary searches, first locate the pivot (the minimum's index, as in Find Minimum), then run a normal binary search on the correct segment (or with an index offset). Also O(log n); more modular, slightly more code.
- Follow-up not covered: with **duplicates** (Search in Rotated Sorted Array II), `nums[s] == nums[mid] == nums[e]` makes the sorted-half test ambiguous, so you must shrink both ends (`s++`, `e--`) and the worst case becomes O(n).
- Good, keep: equality check first, inclusive endpoint on the outer side of each range, and `-1` after the loop.

## 5. Optimal Approach
Binary search on `[lo, hi]` with the invariant "if the target exists, it is in `[lo, hi]`". At each step, return if `nums[mid] == target`. Determine which half is sorted: if `nums[lo] <= nums[mid]`, the left half is sorted. Test whether the target lies inside the sorted half's range using its endpoints. If yes, discard the other half; if no, discard the sorted half. Each step halves the interval: O(log n) time, O(1) space.

## 6. Optimal Java Code
Same algorithm as my submission, with the overflow-safe midpoint and clearer names:

```java
class Solution {
    public int search(int[] nums, int target) {
        int lo = 0, hi = nums.length - 1;
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (nums[mid] == target) return mid;

            if (nums[lo] <= nums[mid]) {                          // left half [lo..mid] is sorted
                if (nums[lo] <= target && target < nums[mid]) hi = mid - 1;
                else lo = mid + 1;
            } else {                                              // right half [mid..hi] is sorted
                if (nums[mid] < target && target <= nums[hi]) lo = mid + 1;
                else hi = mid - 1;
            }
        }
        return -1;
    }
}
```

## 7. Quick Revision
After one cut (rotation), one half of `[lo, hi]` is always sorted: `nums[lo] <= nums[mid]` means the left half is sorted, otherwise the right half is.
Check if the target lies inside the sorted half's endpoint range; if yes go there, otherwise go to the other half. Use `mid = lo + (hi - lo) / 2`.

## 8. Pattern
- Primary: Binary Search on a rotated sorted array (identify the sorted half)
- Secondary: Pivot search + standard binary search (two-pass alternative), Loop invariants

# <span style="color:orange">  Time Based Key-Value Store </span>

## 1. Problem Statement
LeetCode 981 / NeetCode "Time Based Key-Value Store". Design a class `TimeMap`:
- `set(String key, String value, int timestamp)` stores `value` for `key` at `timestamp`.
- `get(String key, int timestamp)` returns the value stored with the **largest** `timestamp_prev <= timestamp` for that key, or `""` if there is none.

Example: `set("alice","happy",1)`; `get("alice",1)` -> `"happy"`; `get("alice",2)` -> `"happy"`; `set("alice","sad",3)`; `get("alice",3)` -> `"sad"`.
Constraints: `1 <= key.length, value.length <= 100`, lowercase letters and digits; `0 <= timestamp <= 10^7`; **all timestamps passed to `set` are strictly increasing**; at most `2 * 10^5` calls. Recommended: O(1) `set`, O(log n) `get`.

## 2. My Approach
My submitted code (unmodified):

```java
class TimeMap {

    HashMap<String,HashMap<Integer,String>> map =null;

    public TimeMap() {
        map = new HashMap<String,HashMap<Integer,String>>();
    }
    
    public void set(String key, String value, int timestamp) {
        HashMap<Integer,String> tm = map.getOrDefault(key,new HashMap<Integer,String>());
        tm.put(timestamp,value);
        map.put(key,tm);
    }
    
    public String get(String key, int timestamp) {
          String val ="";  

         HashMap<Integer,String> tm = map.get(key);
         if(tm==null)return val;

          while(timestamp>=0){
          String  val1 = tm.get(timestamp--);
           if(val1!=null){val = val1;break;}
          }

        return  val;
    }
}
```

A map from key to an inner map `timestamp -> value`. `get` looks up the query timestamp, and if nothing is stored there, steps the timestamp down one at a time until it hits a stored timestamp (or goes below 0).

## 3. Complexity
- `set`: O(1) (but allocates a new inner `HashMap` on every call, even when one exists)
- `get`: O(T) where T is how far the scan must walk down the timestamp line, up to the query timestamp itself (up to 10^7 hash lookups per call). Not O(log n).
- Space: O(total entries), with a heavy boxed `HashMap` per key.
- Correct, but the cost of `get` depends on the **value** of the timestamp, not on how many entries exist.

## 4. What I Missed
- **`get` loops over the timestamp value range, not over the stored entries.** With `set(k, v, 1)` and `get(k, 10_000_000)`, one call does about 10^7 lookups; with up to 2 x 10^5 calls that is far beyond any time limit (worst case, not run by me). Same flaw as scanning the value range in Longest Consecutive Sequence and looping over height levels in Largest Rectangle in Histogram: loop over what exists, never over the value domain.
- **Wrong structure for the query.** The query is a *floor* query ("largest stored timestamp <= t"). A hash map only answers exact matches; floor/predecessor queries need **sorted order** plus binary search (or a `TreeMap`).
- **Missed the key constraint:** timestamps passed to `set` are strictly increasing, so appending to a per-key list keeps it sorted for free; no sorting or ordered insert is needed.
- Eager allocation: `getOrDefault(key, new HashMap<>())` builds a new inner map on every call even when the key exists, and the `put` afterwards is redundant. Use `computeIfAbsent`.
- Binary search shape: this is "find the **last** element satisfying a monotonic predicate" (`timestamp_i <= query` is `T...T F...F`), the mirror of the "first true" template from Find Minimum in Rotated Sorted Array.
- A `TreeMap<Integer, String>` per key with `floorEntry(timestamp)` also gives O(log n) for both `set` and `get` and does not even need the increasing-timestamp guarantee, at the cost of more memory and slower `set`.
- Field names/initialization: `HashMap ... = null;` then assigning in the constructor is unnecessary; declare and initialize `final`.
- Good, keep: returning `""` for an unknown key, and handling a query before the first timestamp (the scan ends below 0).

## 5. Optimal Approach
Store, per key, a list of `(timestamp, value)` pairs in insertion order; because `set` timestamps are strictly increasing, each list is automatically sorted by timestamp, so `set` is an O(1) append. For `get`, binary search the key's list for the **last** entry with `timestamp <= query`: if `list[mid].timestamp <= query`, record its value and search the right half for a later candidate (`lo = mid + 1`); otherwise search the left half (`hi = mid - 1`). Return the last recorded value, or `""` if none. `set` O(1), `get` O(log n).

## 6. Optimal Java Code

```java
class TimeMap {
    private static class Entry {
        final int timestamp;
        final String value;
        Entry(int timestamp, String value) {
            this.timestamp = timestamp;
            this.value = value;
        }
    }

    private final Map<String, List<Entry>> store = new HashMap<>();

    public TimeMap() {}

    public void set(String key, String value, int timestamp) {
        store.computeIfAbsent(key, k -> new ArrayList<>()).add(new Entry(timestamp, value));
    }

    public String get(String key, int timestamp) {
        List<Entry> entries = store.get(key);
        if (entries == null) return "";

        int lo = 0, hi = entries.size() - 1;
        String result = "";
        while (lo <= hi) {
            int mid = lo + (hi - lo) / 2;
            if (entries.get(mid).timestamp <= timestamp) {
                result = entries.get(mid).value;   // valid candidate; look for a later one
                lo = mid + 1;
            } else {
                hi = mid - 1;
            }
        }
        return result;
    }
}
```

## 7. Quick Revision
Per key, keep a list of `(timestamp, value)`; `set` timestamps are strictly increasing, so appending keeps it sorted. `get` is "last timestamp <= query": binary search, record the value whenever `timestamp <= query` and go right (`lo = mid + 1`), else go left.
A hash map cannot answer floor queries; never loop over the timestamp range.

## 8. Pattern
- Primary: Binary Search (last element satisfying a monotonic predicate) on a sorted list
- Secondary: Hash Map of lists, Design, TreeMap `floorEntry` as an alternative

# <span style="color:orange">  Median of Two Sorted Arrays </span>

## 1. Problem Statement
LeetCode 4 / NeetCode "Median of Two Sorted Arrays". Given two sorted (ascending) integer arrays `nums1` (size `m`) and `nums2` (size `n`), return the median of all elements of both arrays. The solution should run in O(log(m + n)) time.
Examples: `nums1 = [1,2], nums2 = [3]` -> `2.0`; `nums1 = [1,3], nums2 = [2,4]` -> `2.5`.
Constraints: `0 <= m, n <= 1000`, `1 <= m + n <= 2000`, `-10^6 <= nums1[i], nums2[i] <= 10^6`. Recommended: O(log(min(m, n))) time, O(1) space.

## 2. My Approach

Merge both sorted arrays into one sorted array (standard two-pointer merge), then read the median: the middle element if the total length is odd, otherwise the average of the two middle elements.

## 3. Complexity
- Time: O(m + n)
- Space: O(m + n) (the merged array)
- Correct on both examples, an empty array on either side, and a single element. Does not meet the O(log) requirement (this is NeetCode's Hint 1 brute force).

## 4. What I Missed
- **The requirement is O(log(min(m, n)))**, not a merge. Merging does work proportional to the input size and fully sorts data when only the middle matters.
- **Key reframing:** the median is determined by a *split* of all elements into a left half and a right half of (nearly) equal size, with every left element <= every right element. You never need the merged order, only where that split falls.
- **Binary search on the split:** take `x` elements from the smaller array `A` and `half - x` from the other array `B` (`half = (m + n + 1) / 2`). Each array is already sorted internally, so the only checks needed are the two cross conditions: `A[x-1] <= B[y]` and `B[y-1] <= A[x]`. If `A[x-1] > B[y]`, `x` is too large; if `B[y-1] > A[x]`, `x` is too small.
- **Sentinels:** use `-infinity` for a left side with no elements and `+infinity` for a right side with no elements; this removes all edge-case branching (an empty array, `x = 0`, `x = m`).
- **Why the smaller array:** it keeps `y = half - x` inside `[0, n]` and makes the search O(log(min(m, n))).
- Even without meeting the target, the merge could be O(1) space: walk both arrays with two pointers only up to the middle position, tracking the last two values.
- Minor: variable `m` holds a median value while `m` is the conventional name for an array size; names like `left`/`right` read better. Good, keep: double arithmetic for the average (no integer overflow, no truncation) and correct handling of an empty input array.

## 5. Optimal Approach
Binary search over `x`, the number of elements taken from the smaller array `A` into the left half; then `y = half - x` come from `B`. The left half is `A[0..x-1] + B[0..y-1]` and the right half is the rest. Define `aLeft = A[x-1]`, `aRight = A[x]`, `bLeft = B[y-1]`, `bRight = B[y]` (with sentinels). The partition is valid when `aLeft <= bRight` and `bLeft <= aRight`. Then the median is `max(aLeft, bLeft)` if `m + n` is odd, else `(max(aLeft, bLeft) + min(aRight, bRight)) / 2.0`. If `aLeft > bRight`, move `hi = x - 1`; otherwise `lo = x + 1`. O(log(min(m, n))) time, O(1) space.

## 6. Optimal Java Code

```java
class Solution {
    public double findMedianSortedArrays(int[] nums1, int[] nums2) {
        int[] a = nums1, b = nums2;
        if (a.length > b.length) { a = nums2; b = nums1; }   // binary search the smaller array

        int m = a.length, n = b.length;
        int half = (m + n + 1) / 2;                          // size of the left half
        int lo = 0, hi = m;

        while (lo <= hi) {
            int x = lo + (hi - lo) / 2;                      // elements taken from a
            int y = half - x;                                // elements taken from b

            int aLeft  = (x == 0) ? Integer.MIN_VALUE : a[x - 1];
            int aRight = (x == m) ? Integer.MAX_VALUE : a[x];
            int bLeft  = (y == 0) ? Integer.MIN_VALUE : b[y - 1];
            int bRight = (y == n) ? Integer.MAX_VALUE : b[y];

            if (aLeft <= bRight && bLeft <= aRight) {        // valid partition
                if ((m + n) % 2 == 1) return Math.max(aLeft, bLeft);
                return (Math.max(aLeft, bLeft) + Math.min(aRight, bRight)) / 2.0;
            }
            if (aLeft > bRight) hi = x - 1;                  // took too many from a
            else lo = x + 1;                                 // took too few from a
        }
        throw new IllegalArgumentException("inputs are not sorted");
    }
}
```

## 7. Quick Revision
The median is a split of all elements into equal halves with `max(left) <= min(right)`; binary search how many elements `x` to take from the smaller array (the other array gives `half - x`).
Valid when `aLeft <= bRight` and `bLeft <= aRight` (use +/-infinity sentinels): too many from A, shrink `x`; too few, grow `x`.

## 8. Pattern
- Primary: Binary Search on the partition point of the smaller array
- Secondary: Divide and Conquer (k-th element of two sorted arrays), Two-pointer merge (brute force), Sentinels
